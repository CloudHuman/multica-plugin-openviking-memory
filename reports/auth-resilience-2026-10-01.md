# 鉴权诊断与失败恢复补修 — 2026-10-01

当前能继续落地的重点是请求预算、错误可追踪性与恢复路径。本轮修复插件侧的两个实际缺口，并保留有界重试策略。OpenRouter 间歇性 401 的确切根因仍未确定。

## 已完成

- 修复 HTTP 超时仅覆盖响应头的缺口：计时持续到读取完整响应体，超时中止请求并释放连接。OV 与 Multica 客户端共用此逻辑。
- 错误诊断区分接口 `http_status` 与错误文本明确携带的模型 `provider_status`，保存认证头是否设置、读取阶段及允许的响应请求 ID。认证值、请求体、URL 查询串和用户信息不进入诊断字段。队列错误诊断随日志持久化，成功或重新受理后清除。
- 提交任务记录过期后，从原生 `.failed.json` 读取模型错误及抽取阶段。读取标记时只有 404 代表不存在；鉴权和网络失败保留待办，状态显示 `polling_errors`，重启后仍保留最后异常。相同持续错误避免重复刷状态日志，恢复后清除当前异常；最终观察超时保留最后错误。
- 管理员可读完整诊断，智能体的 `memory-status` 保留工作区状态与错误说明，省略底层请求诊断字段。

HTTP 诊断的认证标记和响应 ID 描述插件到 OV / Multica 的请求。这些证据不能证明 OV 或 OpenCode 到 OpenRouter 的失败请求是否带了鉴权。原生标记恢复出的 `provider_status` 来自错误文本，未伪装成 OV 接口直接返回的 HTTP 状态。

## 验证

- Node 回归 128/128，含真实 HTTP 连接的慢响应体取消、直接 401 与嵌套模型 401、脱敏、标记恢复、轮询异常重启恢复及超时原因保留。
- 原生 OV 只读核验：复用上一轮真实模型 401 的历史归档，以一个不存在的任务 ID 触发实际 404 和标记恢复，正确识别 `source=archive-marker`、`provider_status=401`、`stage=memory_extraction`，保留 `Missing Authentication header`。禁用重驱，未向 OV 写入新记忆。
- 模板结构校验 2/2，清单与插件打包校验通过。
- 前一轮诊断使用同一凭据：5 次 OpenRouter 鉴权检查、普通与流式 GPT 生成、GLM 生成、OV 容器内原生 SDK 的 embedding 与 GLM 生成均返回 200。这证明当时凭据可用，不能解释或排除之前的间歇性鉴权问题。

本轮没有重跑真实智能体矩阵，也没有把先前的 14/15 改写成全部通过。插件代码需要更新服务后生效。

## 后续优先级

1. 在 OpenCode 与 OV 的模型 SDK 请求边界补充脱敏观测，采集实际失败请求的目标主机、认证头存在性、重定向、状态及上游请求 ID。先捕获失败，再判断客户端、代理或服务端的具体问题；本轮插件诊断覆盖不到这一跳。
2. 针对“评论已发布、最终生成失败”建立交付恢复方案：记录已完成动作及其幂等标识，恢复时从剩余步骤继续。插件无法仅凭模型 401 安全决定重跑整个智能体任务。
3. 扩大固定蒸馏样本，重复验证正式更新与历史值、实体别名、多智能体共享、私聊隔离、临时指令和平台文本过滤。分别统计事实正确率、污染、带来源召回、最终交付与延迟；现有单批样本不足以估算总体质量。
4. 将 OV 模板覆盖的安装、启用和版本检查纳入部署流程，减少只更新插件 ZIP、未加载抽取规则造成的环境差异。
