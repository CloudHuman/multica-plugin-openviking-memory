## 评审发现 → 修复后的实测对照

| 评审时复现的问题 | 现在（真实栈实测） |
| --- | --- |
| 私聊运行的 `task.completed`（`issue_id: ""`）返回非 2xx，5 次后 multica 熔断，之后的评论事件全部被跳过 | R3a：连续 6 次私聊运行后评论照常归档 |
| 工作区 2 管理员用自己安装的 `whsec_` 签名、在请求体里写工作区 1，读到工作区 1 的记忆；工作区 2 的 `memory-status` 列出工作区 1 的归档 | R6：伪造请求 403，冒充安装 401，状态只含本工作区 |
| `ov-*` 门面可写/读/删账号共享的 `viking://resources`、`viking://agent`，智能体之间互相可见 | R4：共享命名空间与他人空间的 URI 一律拒绝 |
| 任意智能体可点名任意 issue 召回其协作记忆 | R5：补丁版按调用它的运行绑定；stock 版明确报告未绑定 |
| stock multica 没有 `GET /v1/tasks/{id}/messages`，运行归档只剩一行"运行完成"噪音 | R2c/R2d：stock 跳过运行事件，以收尾评论代表运行；补丁版归档完整转写 |
| 抽取失败后 `POST /extract` 对已提交的会话是空操作，失败的记录永远缺失 | R7：在新会话代际（`-r1`）重驱并成功抽取 |
| 智能体评论被当作"人类反馈"归档 | R1/R2d：成员 = 人类反馈，智能体 = 智能体陈述 |

## 本轮验证中新暴露并已修复的问题

1. **收尾评论竞态**（补丁版）：运行结束时 multica 同时发出收尾评论与 `task.completed`；评论先到时插件尚不知道该 multica 有任务 API，评论被重复归档。修复：遇到带 `source_task_id` 的智能体评论而能力未知时，先问一次 `GET /v1/tasks/{id}`（只有 200 才据此跳过，404 可能只是超出凭据范围）。回归测试 + R2d。
2. OV 的 `read` 工具的 `uris` 可以是单个字符串，门面此前只检查数组形态。
3. `list` / `tree` / `glob` 以 `viking://` 为默认根，门面现将其映射到调用者自己的空间而不是拒绝。
4. 状态目录锁：同主机同 PID 既可能是自己的上一轮（容器重启），也可能是共享主机名的孪生容器（`network_mode: host`，都是 PID 1）；现在除非持有者可证实已死，都观察心跳再决定。
5. 共享晋升的会话 ID 只精确到毫秒，同毫秒两次运行会冲突；加随机后缀。
6. multica 以新 invocation_id 重投已入队的记录时返回 `duplicate`（此前返回 `queued`，易被误读为重复归档）。

## 测试工具说明

mock 模型从 OV 抽取提示词里挑"最像结论"的一行；OV 会把相邻上下文一起放进提示词，mock 有时挑中别的轮次的句子。真实栈 R3b 因此断言插件可控的部分——归档消息内容与 `peer_id` 归属——而把检索命中数只作为信息输出。
